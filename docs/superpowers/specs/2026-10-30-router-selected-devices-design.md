# Выбор устройств только в Keenetic

## Цель
Пользователь назначает устройству политику VPN Manager в Keenetic. Менеджер автоматически применяет активный профиль к поступающему интернет-трафику, без регистрации IP каждого клиента в панели. Работающий iPhone и остальные устройства сохраняют интернет.

## Подходы
1. Список IP в менеджере — требует двойного управления, пользователь явно отверг.
2. Синхронизация списка клиентов с API Keenetic — требует постоянного доступа к роутеру, хранения его учётных данных и отдельной интеграции. Для задачи не нужна.
3. Принимать перенаправленный трафик домашней подсети на LAN-интерфейсе — предлагаемый подход. Keenetic выбирает клиентов; менеджер знает только границы LAN и применяет один активный профиль.

## Границы и поведение
- Новый режим `router`: домашняя IPv4-подсеть `192.168.1.0/24`, LAN-интерфейс `eth0`. Подсеть задаётся один раз, не для каждого устройства.
- Только входящий через этот интерфейс трафик с источником из указанной подсети и публичным адресом назначения попадает в обработку. Локальные назначения остаются доступны по существующим маршрутам.
- Собственные адреса менеджера и адрес LAN роутера исключаются из захвата; локально созданные соединения менеджера также не захватываются. Ограничения должны проверяться по фактическим адресам интерфейса, а не только по строке из формы.
- Менеджер не перенаправляет на себя трафик всей сети. Фактический выбор остаётся в Keenetic: у устройств без соответствующей политики путь не меняется.
- IPv6 не включается автоматически: в текущей сети внешнего IPv6-маршрута не обнаружено. Поддержка полноценного IPv6 потребует отдельной проверки и настройки.
- Обратная совместимость: существующий режим `profile` с `client_ip=192.168.1.71` продолжает работать до явного переключения.
- Активный профиль, правила доменов, VPN-провайдеры, чужие интерфейсы и основная таблица маршрутов не меняются.
- Отключение распределения оставляет прямой выход для перенаправленных клиентов. Полное удаление этого выхода разрешается только после удаления политик клиентов на роутере.
- При аварии прокси сохраняется блокирующий маршрут, чтобы правила VPN не обходились незаметно. Сохраняются восстановление после перезапуска и проверка владения сетевыми объектами.

## Изменения
- Backend: явный режим области захвата, валидация подсети/интерфейса/исключений, сохранение и восстановление новой области. В API статуса отображаются режим и подсеть.
- Linux: ограниченные правила захвата и NAT для перенаправленной подсети; исключения для роутера и менеджера. Сохраняются существующие механизмы отказа от чужих объектов и отката.
- UI: режим «Устройства выбираются на роутере», настройка LAN один раз, понятный статус и инструкция назначения политики Keenetic. Списка клиентов в менеджере нет.
- Переход с работающего пилота выполняется отдельно от обновления приложения. Переключение области должно быть транзакционным: ошибка возвращает прежний захват и прямой выход, без удаления чужих правил.
- Keenetic: переименовать отображаемую политику `VPN_Manager_iPhone` в `VPN_Manager`, сохранив назначение iPhone; новые устройства автоматически не назначать.

## Проверка и выкладка
1. Тесты валидации и API: несовместимые поля, небезопасные подсети, чужой интерфейс, адреса самого сервера/роутера, прежний формат состояния.
2. Изолированный Linux-тест: два клиента с разными IP одновременно получают правила профиля; неперенаправленный клиент, LAN, роутер и собственные запросы сервера не захватываются.
3. Проверить отключение в прямой режим, падение/восстановление прокси, перезапуск менеджера и ошибки перехода с пилота.
4. Go tests/race/vet, сборка frontend/backend, self-review полного diff.
5. Сохранить состояние и образы, собрать фиксированный commit на сервере, проверить здоровье, переключить существующий iPhone. Добавление второго реального устройства остаётся выбором пользователя в Keenetic.

## Решения исполнителя
Сохранить текущий Go/sing-box/nftables стек и отдельный режим совместимости; не добавлять зависимость от API Keenetic и его паролей. Точное устройство ограниченных Linux-правил определяется реализацией и подтверждается изолированными проверками до выкладки.


## Уточнение после реального захвата пакетов
Keenetic выполняет source NAT при пересылке на шлюз в том же LAN: выбранные клиенты приходят от 192.168.1.1. Первоначальное исключение этого адреса оказалось несовместимо с реальной топологией. Режим router_nat принимает такой перенаправленный трафик, исключая собственные соединения менеджера. Прямой fallback выполняет masquerade и для источника роутера, чтобы возвращаемые в Keenetic пакеты попадали в WAN-политику менеджера. Собственные обычные соединения роутера не направляются на менеджер этой клиентской политикой. Старое поведение сохраняется при router_nat=false; переход поддерживается транзакционно без смены остальных настроек.
