# VPN Manager: управляемый шлюз для одного iPhone

## Цель и согласованный подход
Keenetic 192.168.1.1 направляет интернет-трафик только iPhone Алексей (192.168.1.71, MAC 74:29:59:be:b8:a6) в LXC vpn-gateway 192.168.1.40. VPN Manager по активному профилю отправляет выбранные назначения через Hungary Budapest S4, остальные — напрямую через Keenetic. Локальная сеть доступна напрямую. Остальные устройства не переключаются.

Обсуждались два подхода: отдельный шлюз со своим обслуживанием либо исправление существующего менеджера. Пользователь выбрал менеджер с управлением из панели. Предлагаемая реализация сохраняет Go/Svelte, PostgreSQL, Docker и sing-box. Модуль ядра на Proxmox не устанавливается: используется уже проверенный amneziawg-go внутри контейнера приложения.

## Подтверждённое состояние
- Репозиторий: /Users/akorastelev/GolandProjects/vpn-manager, origin https://github.com/Traliaa/vpn-manager, чистый checkout 42cb1db при обследовании.
- Присланный AmneziaWG-конфиг проверен установленным userspace-клиентом: handshake и HTTPS HTTP 200. Ключи не включаются в репозиторий, тесты, отчёт или логи.
- Сейчас Connect создаёт только kernel interface; importer теряет H1–H4, ядру не передаются и остальные параметры обфускации.
- Для AmneziaWG отсутствует sing-box outbound. Gateway включает NAT, но не прозрачный вход и не направление трафика выбранного клиента по профилю.
- sing-box запускается без контроля дочернего процесса; отдельная служба в LXC занимает порт 1080. Ошибки конфигурации могут не предотвращать показ успешного состояния.

## Предлагаемые изменения
1. Полный перенос поддерживаемых AmneziaWG-параметров импорта и строгая валидация до изменения сети. Существующие JSON-поля сохраняются; новые необязательны. Существующий Budapest-конфиг повторно импортируется/обновляется из исходного файла без дубликата провайдера.
2. Управляемый userspace-клиент как fallback при отсутствии kernel backend: безопасное применение конфигурации, ожидание готовности, контроль PID, корректный Stop/Close/reconnect, cleanup после ошибки. Не подменять AmneziaWG обычным WireGuard. Правдивый статус включает свежесть handshake и диагностическую ошибку.
3. AmneziaWG регистрируется в sing-box как outbound с привязкой к своему интерфейсу и отдельной таблицей маршрутов для этого выхода. Основной default route LXC не меняется. Прямой outbound использует eth0.
4. Управляемый прозрачный TUN-вход sing-box и отдельные правила захвата только источника 192.168.1.71/32; никакого правила для всей /24. Включение из панели задаёт устройство, режим «по активному профилю», текущий статус и кнопку отключения. Настройка сохраняется и восстанавливается после рестарта только после проверки готовности.
5. Существующий NAT-режим API сохраняется совместимым; новый режим получает явные поля и валидацию источника. Пустой список, подсеть вместо /32 или сам адрес менеджера отклоняются в первом пилоте. Применение атомарное: ошибка сохраняет предыдущую конфигурацию. В панели нет успешного статуса при неработающем процессе.
6. Перед переключением телефона готовятся обратимые настройки Keenetic: закрепление IP и отдельная политика для iPhone, основной выход которой — 192.168.1.40. Локальные назначения исключаются, собственный трафик менеджера остаётся в исходной политике. Конкретные команды и возможности этой версии Keenetic проверяются заранее; если политика недоступна, общая DHCP-конфигурация не меняется.

## Семантика трафика и отказов — предложения реализации
- Вначале профиль охватывает youtube.com, googlevideo.com, ytimg.com и anim-ru.net с поддоменами; остальное напрямую. Изменения правил через панель применяются валидированной конфигурацией.
- DNS/сопоставление доменов и TLS/QUIC sniffing проверяются реальными запросами. Общий IP CDN не считается надёжной заменой доменному правилу. Нераспознанный домен соответствует прямому выходу по умолчанию; это явно отражается в ограничениях.
- Назначения, выбранные для VPN, не переходят автоматически в direct при сбое VPN. Остальной интернет продолжает работать. Отключение пилотной политики на Keenetic возвращает iPhone к прежней схеме.
- IPv6 проверяется отдельно. Если нельзя обеспечить аналогичное распределение, пилот ограничивается IPv4 с предотвращением обхода для этого устройства; отключение IPv6 для всей сети недопустимо. До решения IPv6 нельзя объявлять, что весь трафик телефона проходит через менеджер.

## Проверки и выкладка
Unit/regression тесты импорта, lifecycle и cleanup, ошибок применения, /32 allowlist, идемпотентности, генерации правил и совместимости старого gateway API; сборка Go и Svelte; race для lifecycle. Проверка sing-box check до замены рабочей конфигурации. Изолированные Linux-проверки forwarding/DNS/QUIC и поведения при отказе VPN перед пилотом.

После self-review: commit/push в GitHub и сборка на сервере по существующему процессу пользователя. Перед обновлением сверить серверный commit, локальные конфиги, volumes и runtime overrides, сохранить рабочий образ и настройки. БД не мигрировать без необходимости. Старую конфликтующую службу останавливать только при готовой замене с возможностью восстановления.

Приёмка: виден активный Budapest с handshake; через профиль VPN-назначение получает VPN-выход, обычное — прямой; локальные ресурсы работают; пакеты именно iPhone видны на входе менеджера; другие устройства не изменены; отключение/перезапуск и rollback проверены. Фактическую проверку на iPhone пользователь выполняет после переключения; до неё результат обозначается неполным.

## Границы
Не устанавливать kernel modules на Proxmox, не сбрасывать firewall, не менять основной маршрут Keenetic и не включать всю домашнюю/дачную сеть. Секреты остаются на существующих устройствах. Внешний API провайдера VPN не меняется.
